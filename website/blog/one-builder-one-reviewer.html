Start with one builder and one reviewer

Our new starting point for small local apps: one agent owns the complete build, and a second independently checks what people can actually use.

By HeloScrum

IN THIS ARTICLEWhat changed our mindsGive one builder the whole experienceKeep review independentA small team still needs a clear briefJudge the finished work

What changed our minds

We started comparing a single builder with a team of agents on small local projects, including an issue tracker and a browser card game. Splitting the work into rules, interface, visuals, coordination and QA seemed like a reasonable way to use different strengths.

During the card game review, the person playing both versions preferred the single builder’s version so far: it looked better and played better. We had also spent time resolving handoffs, making contracts available across sessions, integrating separate contributions and getting a reviewer into a working browser.

That prompted a practical change. For our next small local HeloScrum projects, we will start with one builder and one independent reviewer who also handles QA.

An observation, with limits.

These are informal comparisons, and the card game comparison is still in progress. The runs used different model mixes and working conditions. They do not establish that team size alone caused the difference, or that a single agent is always faster, better or cheaper.

Give one builder the whole experience

In a small app, design and implementation decisions are often closely connected. Changing a game’s targeting flow can affect the rules adapter, button labels, animation timing, keyboard focus and tutorial. Giving one builder responsibility for the complete interaction keeps those decisions together.

That builder owns the interface, application logic, local persistence, integration and fixes. It can use image generation, libraries and other tools as the work requires. Using a tool does not require creating another standing team role.

The first deliverable should be a usable path through the product: open it, perform its main action, see the result and return safely. Building that path early gives both the reviewer and the human something concrete to assess.

Keep review independent

The second agent has a different job. It examines the submitted work, runs relevant checks and uses the actual app. For a browser game, that includes playing a match. For a local tool, it includes completing its main workflow, trying invalid input and checking whether saved work survives a reload.

The reviewer records what it checked, the exact build, what failed and what remains untested. Passing unit tests, opening a page and completing a real user workflow are different kinds of evidence.

The builder makes the fixes; the reviewer checks them again. If the reviewer implements a feature itself, it cannot also supply independent approval for that contribution. The human retains final acceptance, including whether the product feels good to use.

  1. 01Build a usable versionBuilder owns the complete change.
  2. 02Review the actual appReviewer records evidence and defects.
  3. 03Fix, recheck, acceptBuilder fixes. Reviewer rechecks. Human decides.

A small team still needs a clear brief

Before starting, describe who the app is for, the main thing they should accomplish, the constraints and the evidence needed for completion. Include the run command, supported screen sizes, save boundaries and any actions that require human approval.

For a small project, give the builder ownership of the implementation and integration. Give the reviewer access to the same brief and the runnable candidate. They need a shared understanding of the result, without a separate handoff for every component.

HeloScrum still provides the task board, conversations, working memory and review record. A pair benefits from those features even when it has no dedicated coordinator.

Judge the finished work

We will assess this smaller setup by looking at the usable result: how much intervention it needed, how long it took to reach an accepted build, what review found, how well fixes held up and how the app felt to the person using it.

Usage belongs in that record too, alongside the actual models and tools. Token counts alone cannot settle a cost comparison between different models, and a fast first draft does not include the time needed to make it reliable.

This is our starting configuration for small local apps. When a project presents a clear need for another specialist, we can add one with a specific responsibility. The next post explains how we will make that decision.

Build with a clear brief and a separate review. Try the builder and reviewer workflow.
